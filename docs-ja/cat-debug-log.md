# アプリ側 USB CAT が無応答だった件 — 調査記録

2026年9月3日。UV-K5(8) V3 / JA-K5 ファームウェアで、無線機の**アプリケーション側の
CAT（シリアル制御）が一切応答しない**問題を追った記録です。

結論から書くと、原因は **UART の DMA 受信バッファがアラインされていなかったこと**で、
引き金は**メニュー項目を1つ削除したこと**でした。両者はコード上どこにも接点がありません。

推理を3回外しています。その過程も含めて残します。

---

## 1. 症状

- `dump_regs.py`（自作の CAT ツール）で `0x0514`（版数要求）を送っても **0バイト**
- UV Studio（別実装・WebSerial）でも同じ。「Timeout: no device detected」
- 一方で以下は**すべて正常**
  - ブートローダ経由のファーム書き込み（443ページ完走）
  - UV Studio の画面転送（K5ビューア）
  - IOTCU 公式ファーム `f4hwn.IOTCU_SiEN_v5.9.0_b02.bin` では CAT が完全に動く

## 2. 最初に分かっていたこと

**PC → 無線機の方向は生きていた。**

`0x05DD`（リセットコマンド）を送ると、無線機がその場で再起動しました。

```
1/3 送信                                    ← 1回目の書き込みは成功
WriteFile failed (PermissionError(13, 'デバイスがコマンドを認識できません'))
                                            ← 2回目でUSBデバイスが消えている
```

`case 0x05DD:` は `NVIC_SystemReset()` を呼ぶだけで、タイムスタンプの照合も前提条件も
ありません。**再起動したということは、フレームが届き、難読化が解かれ、CRC が通り、
ディスパッチまで到達している**ということです。

つまり壊れているのは**返信の経路だけ**、という前提でしばらく動きました。この前提自体は
正しかったのですが、原因の場所を大きく取り違えました。

## 3. 外した推理 その1 — 存在しないコマンドを送っていた

レジスタ読み出しに使う `0x0601` が、そもそもビルドに入っていませんでした。

```c
#ifdef ENABLE_UART_RW_BK_REGS
        case 0x0601:
            CMD_0601_ReadBK4819Reg(Port, pUART_Command->Buffer);
            break;
#endif
```

```
ENABLE_UART_RW_BK_REGS:BOOL=FALSE
```

`case` ごと消えるので、コマンドは switch を素通りして**無言で捨てられます**。返信も
エラーも出ません。通信路が死んでいるのと区別がつきません。

これは実在の問題だったので有効化しました（コスト68バイト）。ただし `0x0514` は元から
実装済みで、そちらも無応答だったので、**主犯ではありませんでした**。

## 4. 外した推理 その2 — 送信関数の使い分け

同じ USB IN エンドポイントに書く関数が2つあり、片方だけが完了を待っていませんでした。

```c
// 画面転送（動いていた）
ep_tx_busy_flag = true;
usbd_ep_start_write(CDC_IN_EP, buf, size);
while (ep_tx_busy_flag && --timeout);      // 完了を待つ

// CAT返信（動いていなかった）
usbd_ep_start_write(CDC_IN_EP, buf, size); // 待たない
```

「連続で流している画面転送は動き、たまに1回送る CAT が動かない」という症状に合うので、
待つように変えました。**効果なし。**

## 5. 外した推理 その3 — IN FIFO の詰まり

CherryUSB の PY32 移植層を読むと、こう書かれています。

```c
int usbd_ep_start_write(const uint8_t ep, const uint8_t *data, uint32_t data_len)
{
  ...
  if (USB->IN_CSR1 & USB_INCSR_IPR)
  {
    pyusb_set_active_ep(old_ep_idx);
    return -3;                          // 何も送らずに帰る
  }
```

`IPR` は InPktRdy。前のパケットが未回収だと送信を拒否して `-3` を返す。そして
**呼び出し側は誰もこの戻り値を見ていませんでした**。

リトライを入れたところ、**無線機がフリーズしました**。レジスタ128本ぶん空回りしたためです。

このフリーズ自体は情報でした。「IPR が一時的に忙しいのではなく、立ちっぱなし」と読めます。
そこで `USB_INCSR_FF`（Flush FIFO）で流してから書くようにしました。**効果なし。**

> ここまでで firmware を3回書き換え、3回とも無関係でした。うち1回はフリーズを新たに
> 作り込んでいます。**症状から原因を推理する方針そのものが間違っていました。**

## 6. 転換点 — 他人の実装で同じことをやる

IOTCU 公式ファームを焼いて、UV Studio でキャリブレーションをダンプしました。

```
[5:11:37] Message received: type=0x0515
[5:11:37] Device: F4HWN v5.9.0
[5:11:37] Dump complete! 👍🏼
```

**動きました。** 同じ無線機、同じケーブル、同じPC、同じ UV Studio。

これで確定したこと。

- ホストの言語もシリアルスタックも無罪（Python/pyserial と JS/WebSerial の両方で落ちていた）
- ケーブルもハードウェアも無罪
- **原因は私たちのビルドの中にある**

そして、それまでに書いた USB の修正3つは全部撤回しました。原因でないものを触った差分を
抱えたままにする理由がありません。

## 7. 二分探索

推理をやめて、ビルドフラグを機械的に潰しました。

| 版 | 内容 | 結果 |
|---|---|---|
| A | JA-K5 から USB 修正3つを撤回 | ✗ |
| B | A から SI4732・レジスタ画面・レジスタ読出しを全部 OFF | ✗ |
| C | A から K5ビューアを OFF | ✗ |
| D | A から起動チャイムを OFF | ✗ |
| E | D からさらに内蔵起動ロゴを OFF | ✗ |
| **F** | **自分のソースを上流と同一構成でビルド（日本語化なし）** | **✓** |
| **G** | **F に日本語化だけ追加** | **✓** |
| H | G から Fox Hunt だけ OFF | ✓ |
| I | G から RF LOG だけ OFF | ✓ |
| **J** | **G に `ENABLE_FIXED_NAV_K5` だけ ON** | **✗** |
| K | G から Fox Hunt と RF LOG を両方 OFF | ✓ |

F と G が動いた時点で「コードは無実、フラグの問題」と分かり、B と G の構成差を機械的に
洗い出したところ4つに絞れました。3つは単独で無害（H・I・K）。残った1つが J です。

`ENABLE_FIXED_NAV_K5` は私が追加したフラグで、やっていることは2つだけです。

```c
// 1. 起動時に上下キーの向きを固定する
gEeprom.SET_NAV = true;
```

```c
// 2. メニューから該当項目を1つ削除する
#ifndef ENABLE_FIXED_NAV_K5
    {"SetNav",      MENU_SET_NAV       },
#endif
```

分離してもう一度。

| 版 | 内容 | 結果 |
|---|---|---|
| L | `SET_NAV = true` だけ（メニュー項目は残す） | ✓ |
| **M** | **メニュー項目の削除だけ**（SET_NAV は固定しない） | **✗** |

**メニューから項目を1つ消すと、USB の CAT が死ぬ。**

## 8. リンカマップ

L と M のメモリ配置を突き合わせました。

```
L（動く）
  20001de4 +78    gMenuIndices
  20001e32 +1     gMenuCursor
  ...
  20001e3a +256   UART_DMA_Buffer      ← 偶数番地
  20001f3a +152   VCP_ReplyBuf

M（落ちる）
  20001de4 +77    gMenuIndices          ← 1バイト縮む
  20001e31 +1     gMenuCursor
  ...
  20001e39 +256   UART_DMA_Buffer      ← 奇数番地に着地
  20001f39 +152   VCP_ReplyBuf
```

`gMenuIndices` は `ARRAY_SIZE(MenuList)` で寸法が決まります。

```c
uint8_t gMenuIndices[ARRAY_SIZE(MenuList)];
```

メニュー項目を1つ消すと `MenuList` が1要素縮み、この配列も1バイト縮み、**それ以降の
`.bss` が全部1バイトずれます**。その中に `UART_DMA_Buffer` がありました。

そして `VCP_ReplyBuf` — **CAT の返信を組み立てるバッファ** — が、その真後ろに
**隙間ゼロで**隣接しています。

## 9. 原因

`UART_DMA_Buffer` は物理 UART の**循環DMA受信先**です。

```c
DMA_InitStruct.Mode = LL_DMA_MODE_CIRCULAR;
DMA_InitStruct.MemoryOrM2MDstAddress = (uint32_t)UART_DMA_Buffer;
DMA_InitStruct.NbData = sizeof(UART_DMA_Buffer);
```

マイク端子に何も挿していなくても RX ピンは開放でノイズを拾うので、**このDMAは常時
走っています**。ケーブルの有無に関係なく。

その転送先が奇数番地に落ちると、隣の `VCP_ReplyBuf` を踏みます。ホストが待っている
返信そのものが上書きされる。

**検証**：修正前後で `VCP_ReplyBuf` との隙間は**どちらも0バイト**。変わったのは
アラインメントだけです。

```
M（落ちる）: UART_DMA_Buffer 20001e39+256  終端 20001f39  VCP_ReplyBuf 20001f39  隙間 0
N（動く）  : UART_DMA_Buffer 20001e3c+256  終端 20001f3c  VCP_ReplyBuf 20001f3c  隙間 0
```

## 10. 修正

```c
uint8_t UART_DMA_Buffer[256] __attribute__((aligned(4)));
```

1行です。

**このバッファもDMA設定も上流のコードそのままです。** 上流のビルドでは偶然アライン
されていて、誰も踏んでいませんでした。メニュー項目を増減する改造をすれば、誰でも
踏み得ます。

## 11. 教訓

**「そもそも動くはずの機能か」を最初に確認する。**
CHIRP が USB-C 直結で動くことは上流の Wiki に書いてありました。それを知っていれば、
自分のコードより先に環境と構成を疑えたはずです。

**他人の実装で同じことを試すのを、もっと早くやる。**
IOTCU 公式ファームで動いた瞬間、探索範囲は半分になりました。これは調査開始から
数時間後ではなく、最初の30分でやるべきでした。

**症状から原因を推理するより、差分を機械的に潰すほうが速い。**
推理は3回外れました。二分探索は11回のフラッシュで犯人にたどり着きました。

**症状が変わったこと自体が情報になる。**
リトライを入れてフリーズしたのは失敗ですが、「IPR が一時的でなく恒久的に立っている」
という事実は、そこで初めて見えました。

**無関係に見える2つが繋がっていることがある。**
「メニュー項目を消す」と「USB の返信が消える」の間には、コード上の接点が一切
ありません。繋いでいたのはリンカでした。

## 12. 再現手順

上流の armel/uv-k1-k5v3-firmware-custom v5.9.0 で確認できます。

1. `App/ui/menu.c` の `MenuList[]` から項目を1つ削除する（どれでもよい）
2. Fusion 構成でビルドして書き込む
3. 通常起動させ、UV Studio でキャリブレーションのダンプを試す
4. リンカマップで `UART_DMA_Buffer` のアドレスを確認する

奇数番地に落ちていれば再現します。`__attribute__((aligned(4)))` を付ければ直ります。
